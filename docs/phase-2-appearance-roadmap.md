# dsh-cyberwhale 第二阶段美化功能开发路线

本阶段把插件扩展为「桌宠 + Harness 外观设置」：保留桌宠，新增独立的主题页面，支持浅色和深色预设、自选颜色、字体、壁纸及图片取色。本文件同时作为可行性报告、范围约定和后续验收清单。

**结论：可以在同一个插件里实现主要功能，但不能承诺所有窗口都能改。** 配色有官方接口；macOS 主窗口已有原生磨砂材质，主窗口的原生 Liquid Glass 需要桌面壳接入能力。自有桌宠窗口可以独立接入原生材质，气泡开关已在本地预览中实现。

核查日期：2026 年 10 月 2 日，Asia/Shanghai。本文件保留 `0.2.0-preview.1` 阶段的核查和路线记录；当前正式版本为 `1.0.0`，macOS 与 Windows 日常使用已由维护者确认，最新产品范围见 [README](../README.md)。以下「官方事实」来自原核查基线的文档和源码；「方案」及难度为本项目的工程判断。历史实施状态和缺项见第 9、12 节。

## 2 功能可行性和困难

下表的「可做」表示已有实现途径，不表示已经完成原型或跨平台验证。

| 功能 | 判断 | 难度 | 主要困难与处理方式 |
|---|---|---|---|
| 一个插件包含桌宠和美化 | 可做 | 低 | 分开设置、配置和生命周期；关闭桌宠仍能使用主题 |
| 两个独立设置页面 | 可做 | 低 | 用官方 `settings.section` 分别注册「桌宠」「主题」 |
| 浅色、深色、跟随系统 | 可做 | 低 | 沿用官方主题状态，不另建一套系统外观监听 |
| 分别选择浅色和深色预设 | 可做 | 中 | 插件保存两份选择，官方状态决定当前使用哪一份 |
| 强调色、背景色、文字色组合 | 可做 | 中 | 需要完整的状态色和表面层级映射，不能只替换三个颜色 |
| Codex 风格预设 | 可做 | 中 | 参考公开颜色及开源色板，自行实现派生色；完整算法未由官方文档公开 |
| UI 字体和代码字体 | 可做，需覆盖检查 | 中 | CSS 字体变量可覆盖，但终端、预览器及原生窗口有独立边界 |
| 正文大小 | 官方已支持 | 低 | 当前安装包接受整数 `10–22 px`；它不是全软件缩放 |
| 全 UI 字号和独立代码字号 | 有条件可做 | 中至高 | 没有同等完整的官方设置入口，需逐组件验证；列为后续增强 |
| 静态壁纸、渐变和切换背景 | 可做，先验证挂载方式 | 中 | 当前没有专用壁纸接口；需处理不透明内容层、资源读取和层级 |
| 图片取色并生成深浅两套配色 | 可做 | 中 | 有成熟算法，仍需转换为 Harness 的颜色角色并检查可读性 |
| 页面内磨砂玻璃 | 可做，属于 Web 效果 | 中 | CSS 模糊采样页面后方内容，不能直接采样应用外桌面 |
| 利用 macOS 已有原生磨砂 | 有条件可做 | 中 | 主窗口已有 vibrancy，可调整页面覆盖层；材质类型和强度由壳及系统决定 |
| macOS 主窗口原生 Liquid Glass | 当前插件接口不足 | 高 | 需要主进程窗口句柄、原生视图桥接及 macOS 26 能力支持 |
| Windows 主窗口 Mica 或 Acrylic | 当前插件接口不足 | 高 | Electron 能力不等于插件能力；需官方桌面壳提供入口 |
| 大面积折射、动态视频壁纸 | 技术上可研究，推迟 | 高 | 渲染开销、输入与滚动体验、平台差异，先完成静态方案 |

主题和字体的入口依据是官方 [主题包说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-theme/README.md)；设置页面依据是 [设置包说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-settings/README.md)。壁纸和整体美化的具体产品方案由本项目设计，官方没有承诺这些现成功能。

## 3 哪些界面可以改变

### 可以纳入主题覆盖的范围

官方把界面颜色集中为 CSS 变量，可理解为有名称的颜色角色。主题服务生成快照，由布局服务应用到页面；不需要替换整个官方布局。[官方样式规范](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/web-styling.md)、[布局服务说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-layout/README.md)

| 界面部分 | 本阶段允许调整 | 必须保留的行为 |
|---|---|---|
| 左侧导航和会话列表 | 背景、文字、选中与悬停色，适配覆盖层透明度 | 会话操作、折叠、拖动分栏、键盘导航 |
| 中间对话区 | 背景、正文和次要文字、链接与选择高亮 | 内容结构、滚动和文字选择 |
| 输入框和工具栏 | 表面、边界、按钮、占位文字、焦点颜色 | 输入、附件、发送、停止、禁用状态 |
| 右侧文件和详情面板 | 由公共变量控制的背景、文字和分隔线 | 面板切换、尺寸、文件操作 |
| 设置和插件管理页 | 公共表面、文字、开关与强调色；新增主题页面 | 官方配置流程和错误提示 |
| 菜单、提示、弹窗 | 主题拥有的公共颜色和材质变量 | 层级、遮罩、焦点、点击外部关闭等行为 |
| 代码块和差异视图 | 可覆盖的表面、文字、增删色和代码字体 | 行号、列对齐、增删含义；语法高亮单独核对 |
| 桌宠气泡 | 作为可选功能跟随主题 | 桌宠状态机、点击命中与窗口位置 |

「可覆盖」的最终范围由原型截图逐项确认。iframe、WebView、终端画布、PDF 和保留文档原色的预览内容，不会因为主页面颜色变量改变就自动跟随。

### 必须固定或另行处理的范围

这里的固定是指保持官方平台边界和行为，不是要求某个十六进制颜色永久不变。

| 部分 | 第二阶段边界 |
|---|---|
| macOS 红黄绿按钮、系统窗口外框与圆角 | 保留系统控件和命中区域，不用主题覆盖其位置或行为 |
| Windows 标题栏按钮与拖动区域 | 保留官方几何和系统操作；已有颜色同步能否跟随新色板需真机验证 |
| 系统菜单、文件选择器和原生确认框 | 可随系统深浅外观，不能保证任意自定义颜色 |
| 登录、欢迎、强制更新和独立账户窗口 | 不属于普通插件主页面；不承诺与主题全量一致 |
| 内嵌网站、PDF、图片和外部编辑器 | 保持其自身渲染；只调整外围面板 |
| 三栏结构、响应式布局和分栏尺寸规则 | 第二阶段沿用官方实现；替换 `root` 等核心占位属于另一项开发 |
| 错误、警告、成功、授权和代码增删信息 | 颜色数值可以适配，但含义与文字、图标提示必须保留 |
| 焦点、可读性、减少动态效果和系统降低透明度 | 效果不能覆盖这些用户需求；缺少原生状态入口时提供手动关闭特效 |

主窗口、独立窗口及隔离 preload 的边界可见 [官方桌面说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/desktop/README.zh.md) 和 [发布版 preload](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/apps/desktop/src/preload-app.ts)。

## 4 主题和颜色方案

### 使用官方主题覆盖接口

已核实当前安装包具有 `getTheme()`、`setTheme()`、`register()`、`overrideTokens()` 和 `theme/change`。`overrideTokens(source, tokens)` 接受每个变量的 `{ light, dark }` 字符串对，返回撤销函数；同一来源重新写入会替换整层，多个来源按顺序叠加，后写入的同名变量生效。[发布版主题接口源码](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/packages/client/ui-theme/src/client/index.ts)

**方案：保持官方的 light、dark、system 模式，用一个属于本插件的覆盖层应用深浅配色。** 本插件自己保存预设名称、自选颜色等偏好。这样不必依赖第三方主题 ID 的官方持久化，也不会把 system 变成某个固定颜色模式。

接口形状示意，供后续原型核对，不是本次已实现的代码：

```js
ctx.effect(() => ctx.theme.overrideTokens('dsh-cyberwhale.appearance', {
  '--dsw-alias-bg-base': {
    light: '#FFFFFF',
    dark: '#181818',
  },
  '--dsw-alias-label-primary': {
    light: '#0D0D0D',
    dark: '#FFFFFF',
  },
}));
```

这两项只展示调用方式。正式预设必须覆盖一组配套变量，不能以这个示例充当完整主题。关闭美化时撤销覆盖层，恢复被它覆盖的官方或其他插件主题；不擅自删除其他主题插件的样式。

## 5 字体和设置页面

### 字体范围

第一批支持 UI 字体族、代码字体族和官方正文大小。现已通过 `queryLocalFonts()` 读取界面所在电脑的已安装字体家族，提供下拉选择与系统默认选项；按家族去重，不将粗细样式重复列出。每次进入主题页在页面就绪后自动读取一次，正常状态不显示刷新按钮；失败时才提供重新读取和手动输入，保留现有配置。重新进入页面会更新列表，页面关闭后的旧请求不会覆盖新页面。中文、英文及等宽字体保留回退，暂不自动下载字体。

该接口依赖安全上下文及窗口的 `local-fonts` 权限，使用浏览器公开接口，不需要增加 Harness 原生桥接或启动桌宠。已核对本机 Harness 主窗口的安全协议与权限处理，并在独立无界面 Chromium 中验证：权限已允许、没有用户手势时也可自动读到 252 个本机字体家族。需要手势或授权的其他环境仅在自动读取失败后显示重试入口。没有操作 Harness 界面，Windows 实机仍待验收。依据：[Chrome 本地字体访问说明](https://developer.chrome.com/docs/capabilities/web-apis/local-fonts)与 [Electron 权限文档](https://www.electronjs.org/docs/latest/api/session#sessetpermissionrequesthandlerhandler)。

正文大小调用官方 `setFontSize()`，按运行时实际范围生成控件。UI 字号和代码字号独立控制放到增强阶段，分别验证聊天、菜单、设置、表格、代码行和差异行；终端字体通过其自身服务核对，不能以修改 CSS 变量就承诺覆盖终端。

字体变量在父子节点上的解析、被固定样式覆盖的组件，以及中文字体实际命中，是原型检查项。新增字体不得使代码列对齐或输入框高度异常。

### 两个独立页面

同一个安装包注册两个 `settings.section`：

| 页面 | 内容 |
|---|---|
| 桌宠 | 现有启用、大小、眼睛跟随、气泡、位置及运行时设置 |
| 主题 | 美化开关、模式、深浅预设、自选颜色、字体、背景和效果 |

主题页按「外观模式和预设 → 自选颜色 → 字体 → 背景 → 视觉效果」排列。高级项折叠，页面持续显示一块组合预览。配色、字体、背景与特效修改后即时生效并自动保存，不设置额外确认栏；连续操作串行保存最后的选择。写入失败恢复已保存配置并明确提示，多窗口旧配置不能覆盖新配置。

主题功能不要求下载桌宠 Electron 运行时：它运行在 Harness 已有页面里。关闭桌宠不关闭主题；关闭美化不影响桌宠；卸载整个插件则撤销两者的活动效果。

## 6 壁纸和图片取色

### 背景切换

**方案：第一批提供纯色、预设渐变、本地静态图片三种背景。** 支持替换、移除、填充或适应、显示位置，以及遮罩和模糊强度。浅色和深色可以共用图片或分别选择。手动切换及模式切换优先；定时轮播留到后续，视频和动画壁纸推迟。

官方三栏有各自的背景，直接设置 `body` 壁纸可能被挡住。`shell.overlay` 位于内容上方，也不是现成的背景插槽。因此原型必须先验证一个插件拥有的背景层，配合指定表面的覆盖透明度，不能直接把 overlay 当成壁纸层，也不能依赖打包后变化的 CSS 类名。[发布版布局样式](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/packages/client/ui-layout/src/client/AppFrame.module.css)

本地预览现已将壁纸扩展到整个 Web 外壳底层：利用公开的 root 占位与 shell overlay 座位识别共同框架，仅挂载独立装饰层，不替换 root 或占用 overlay。图片按窗口尺寸固定铺设，不随侧栏收放、拖动或聊天切换改变裁切；侧栏叠加 Web 磨砂采样这张图片。代码、输入框和弹窗保留足够的表面遮罩。背景层不拦截点击、选字、滚动或窗口拖动。独立原生窗口和嵌入内容仍不在通用壁纸适配范围内。

本地图片复制到本插件的用户数据目录，设置只保存资源 ID，不依赖原图永久留在某个路径。通过经过鉴权的资源接口读取；在 `dsh-app://app/` 下验证 URL、内容类型、缓存和 CSP。先限制为解码后的 PNG、JPEG、WebP，确定文件及像素上限，压缩大图；失效时回退纯色。远程图片和可执行内容格式不在首版范围内。

### 图片取色

可采用 Google 的 Material Color Utilities。官方提供 TypeScript 实现及图像量化、颜色评分、HCT 色彩空间、动态色板和对比度工具；这些能作为算法基础，但不会直接输出 Harness 的全部颜色角色。[算法库说明](https://github.com/material-foundation/material-color-utilities/blob/main/README.md)、[动态配色指南](https://github.com/material-foundation/material-color-utilities/blob/main/dev_guide/creating_color_scheme.md)

本项目的处理流程：

1. 在本机解码并缩小图片，忽略透明像素，生成候选颜色。
2. 给出多个候选主色，让用户选择；可以重新取色或固定现有主题。
3. 从主色生成浅色和深色两套表面、正文与强调色。
4. 转换为 Harness 变量，独立保留错误、警告和代码增删的含义。
5. 对组合后的颜色检查对比度，修正不能阅读的颜色并显示预览。
6. 保存最终配色、算法版本和图片资源 ID，启动时不必重新处理整张图。

换壁纸是否同时更新主题提供单独开关，默认先预览再应用。全黑、全白、低饱和、多色、透明及人物图片都需要覆盖；不能简单使用整张图片的平均 RGB 作为全部主题色。取色在 Worker 或等价的异步任务中完成，取消旧任务，防止快速换图把旧结果应用到新图。

### 可读性标准

普通文字目标至少 `4.5:1`，符合大字号条件的文字和需要识别的非文字控件目标至少 `3:1`，并检查选中、悬停、禁用和焦点状态。[WCAG 2.2](https://www.w3.org/TR/WCAG22/#contrast-minimum)、[非文字对比度](https://www.w3.org/TR/WCAG22/#non-text-contrast)

自选颜色和公开预设都要检查。例如 `#0285FF` 与白色的计算对比度约为 `3.62:1`，不能直接把它当成所有白底小字号链接的颜色。需要为相应角色派生更合适的色值。壁纸和玻璃的最终背景会变化，不能只检查原始色板；阅读表面要有能保证对比度的遮罩，无法保证时使用实色表面。

## 7 原生磨砂和液态玻璃

### 四种效果分开定义

| 效果 | 实际能力 | 本项目安排 |
|---|---|---|
| Web 磨砂 | `backdrop-filter` 模糊页面内部后方内容，可配合壁纸、边缘和阴影 | 可进入第二阶段，先验证性能和层级 |
| macOS vibrancy | 原生磨砂材质；官方主窗口当前已启用 `sidebar` | 利用现有材质，验证主题覆盖层；不宣称是 Liquid Glass |
| macOS Liquid Glass | Apple 原生玻璃效果，例如 AppKit `NSGlassEffectView`，属于 macOS 26 系列能力 | 单独研究，等待或推动官方窗口接口 |
| Windows Mica 和 Acrylic | Windows 原生背景材质，有各自平台限制 | 作为未来原生适配；当前主窗口插件没有配置入口 |

官方发布版主窗口在 macOS 使用 `vibrancy: 'sidebar'` 和透明窗口背景，页面侧栏再叠加颜色。Windows 欢迎窗口中的 Acrylic 不能推导成插件能为主窗口切换材质。[官方窗口源码](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/apps/desktop/src/main.ts)

Electron 的 `setVibrancy()` 和 `setBackgroundMaterial()` 是主进程窗口 API；后者文档要求 Windows 11 22H2 及以上。它们不会自动成为 Harness 插件 API，也不能把 vibrancy 当成 Liquid Glass。[Electron 窗口文档](https://www.electronjs.org/docs/latest/api/browser-window#winsetvibrancytype-options)、[Windows 材质 API](https://www.electronjs.org/docs/latest/api/browser-window#winsetbackgroundmaterialmaterial-windows)

### 原生 Liquid Glass 的阻碍和可行路径

当前 `dshDesktop` 桥接提供浏览器、快捷键、设备信息和更新等能力，没有开放设置主窗口玻璃材质或取得原生视图的接口。宿主插件也运行在独立 Host 中。**因此仅在 npm 插件内加入原生模块，无法通过现有公开接口给 Harness 主窗口附加 Liquid Glass。** 我们自己的桌宠 Electron 窗口已通过 Node-API 插入 `NSGlassEffectView`，只用于可选气泡材质，不改变 Harness 主窗口。[发布版桥接源码](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.2/apps/desktop/src/preload-app.ts)

可行的后续路径是向上游提出或贡献一个受控的窗口外观服务，由官方主进程执行材质操作。建议能力包括：查询支持的材质、应用或撤销插件请求、同步系统透明度和对比度偏好，以及恢复默认材质。具体接口名称待上游确定，本项目不假定它已存在。

如果需要原生模块，还要处理 macOS 版本检测、arm64 与 x64 构建、Node 或 Electron ABI、签名、窗口尺寸与全屏、视图层级和点击命中。自行 fork 桌面客户端虽可研究，却会成为另一种分发和升级路线，不列入普通插件第二阶段的默认方案。

Apple 建议把玻璃用于浮在内容上的控制和导航层。因此即使以后具备原生入口，也优先用于侧栏和少量浮动控制，正文和代码阅读区保持稳定表面。效果说明和系统要求参考 [NSGlassEffectView](https://developer.apple.com/documentation/appkit/nsglasseffectview) 与 [Apple Liquid Glass 设计说明](https://developer.apple.com/videos/play/wwdc2025/219/)。

### 降级规则

系统不支持、用户降低透明度、增强对比度或关闭特效时，回退为配套的实色表面。Web 磨砂不得标注成「原生 Liquid Glass」。页面内模拟效果与原生材质分别显示状态；当前没有原生入口时不显示可点击却无效的原生玻璃开关。

## 8 代码结构和配置方案

以下为当前本地原型的模块职责。最初规划的文件名已按实际实现调整。

| 位置 | 当前职责 |
|---|---|
| `client/index.js` | 保留桌宠入口，组装两个设置页面 |
| `client/appearance-page.js` / `appearance-css.js` | 主题页、组合预览、背景类型对应设置与 Web 磨砂样式 |
| `client/appearance-runtime.js` | 颜色覆盖层、整窗背景、系统模式响应、自动保存与生命周期 |
| `client/appearance-image.mjs` | 图片解码、缩放、压缩、主色提取与浅深方案生成 |
| `lib/appearance-model.cjs` | 预设、配置校验、配色派生与可读性修正；格式版本迁移尚未实现 |
| `lib/appearance.js` | 独立主题配置的原子保存、修订冲突保护、壁纸资源保存/读取与缓存清理 |
| `lib/index.js` | 接入美化配置和资源接口，复用现有鉴权方式 |
| `docs/theme-presets.md` / `LICENSES/theme-palettes.txt` | 固定版本主题的来源及许可记录；基础色值存于共享模型 |
| `helper/bubble-glass.js` / `helper/native/` | 自有桌宠窗口的可选原生气泡材质及不支持时的降级 |
| `tools/` | 主题覆盖、对比度、卸载恢复及跨平台验证 |

建议沿用 `$DSH_HOME/dsh-cyberwhale/` 保存用户数据：现有 `settings.json` 继续保存桌宠，新建 `appearance.json` 保存美化，`wallpapers/` 保存导入图片。路径从已有 `resolveDshHome()` 推导，不硬编码 macOS 用户目录。

美化配置至少包含：`schemaVersion`、美化开关、深浅预设与自选颜色、字体、壁纸资源、取色开关与结果、Web 效果参数。官方模式和正文字号通过官方服务修改，不在两个地方持久化相互冲突的同一设置。多窗口同步复用官方通知服务或增加明确的修订通知；单窗口立即生效不代表已经解决多窗口一致性。

客户端增加主题服务依赖及对应包声明，在拥有服务的上下文中应用覆盖层；主题能力缺失时提供清晰的兼容状态，不阻塞桌宠。监听器、覆盖层、背景节点和预览任务都必须有卸载清理。禁用与热重载后不能留下残余颜色或重复背景。

本阶段发布仍是同一个 npm 插件。开发目录、构建产物和 Harness 的安装目录仍需区分；修改工作区不会自动改变通过 npm 安装的副本。每次验收记录实际加载的插件版本，不仅记录仓库版本。[现有开发指南](development.md)
